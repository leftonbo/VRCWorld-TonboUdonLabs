# string・VRCUrlは512フィールド、int・long配列は1024要素まで保持

> 過去の検証記録です。現在の構成・結果・操作手順は[最新レポート](../../Reports/2026-10-01-playerobject-persistence.md)を参照してください。
> 以下のケース数・未確認事項・メニュー操作は当時の記録です。初期セットアップ用のエディタ拡張は削除済みです。

[添付TSV](raw-client-restored-20261001-201041.tsv)の92ケースを集計した。
string・VRCUrlの全14ケースと、int[]・long[]の全40ケースで、全値が期待パターンと一致した。
今回置いたケースでは、string・VRCUrlのフィールド数と配列の要素数の上限は見つからなかった。
固定長スカラーの境界は前回と同じで、使用量APIの取得値は49640 / 102400 Bだった。

## 追加ケースはすべて保持、上限は未測定

| 対象 | 今回試した個数 | 最大ケースの結果 |
|---|---|---|
| stringの同期フィールド数 | 128, 129, 130, 255, 256, 257, 512 | 512/512一致 |
| VRCUrlの同期フィールド数 | 128, 129, 130, 255, 256, 257, 512 | 512/512一致 |
| int[]の要素数 | 1, 15, 16, 26, 27, 28, 31, 32, 33, 63, 64, 65, 127, 128, 129, 255, 256, 257, 512, 1024 | 1024/1024一致、長さ1024 |
| long[]の要素数 | 同上 | 1024/1024一致、長さ1024 |

配列は1ケースに1個の同期フィールド。配列フィールドの個数を増やした結果ではない。
全40配列で実際の長さと期待要素数が一致し、intは10101から、longは5000010101からの連番が完全一致した。
string27フィールドとJSON4096文字1フィールドの既存対照も保持された。
今回の値パターンと検証条件で、上記の配置個数が保持されたという結果であり、未測定の個数・値・構成での保持を保証するものではない。

## 固定長スカラーの失敗は再現し、全体容量は取得時点で上限未達

既存41ケースの復元一致数は、前回19:24のRejoin直後TSVとすべて一致した。
固定長18型の境界対照は、保持側18ケースが全値一致、失敗側18ケースが全値既定値。
全92ケースでは74ケース保持、18ケース失敗で、部分一致やNULLはない。復元列と現在列も全行で一致した。

int27個・long16個のスカラーフィールドは失敗する一方、int[1024]・long[1024]は保持されている。
値部分の計算値では、int配列が4096 B、long配列が8192 Bで、スカラーの失敗側の108 B・128 Bを超える。
この比較は、値部分の単純な合計サイズや、すべての型に共通するフィールド数上限だけでは説明できない。
前回の128に関する式は固定長スカラーフィールドに適合した仮説であり、string・VRCUrl・配列の上限式としては使わない。
固定長スカラーと可変長・配列では、内部の保存処理やレコードの扱いが異なる可能性がある。内部形式や失敗箇所は未確認。

| 使用量APIの記録 | 値 |
|---|---|
| 全体の使用量 | 49640 B（上限の約48.5%） |
| 全体の上限 | 102400 B |
| 上限との差 | 52760 B |
| 更新待ち | False |
| 更新イベント取得日時 | 2026-10-01 20:10:02.5699163 JST |

使用量はローカルプレイヤーのPlayerObject全体に対するAPIの取得値で、特定ケースの保存量ではない。
取得時点で上限未達だが、このTSVは退出前の容量変化を記録していない。
ClientSimで取得された247905 Bとは別の実クライアントの観測であり、両者を同じ容量測定として扱わない。
post_success・sent_bytesは全件unavailableで、Rejoin後の未送信観測と整合する。cloud_commit_ackもunavailableで、APIの更新はクラウド保存完了通知ではない。
クライアント版、プラットフォーム、退出前の操作・待機時間は添付TSVにはない。

配列の要素数をさらに増やすなら1024より上を調べる。内部形式の原因を絞るなら、固定長スカラーとstring・配列を混ぜたケースや、型の並び順を変えたケースが候補になる。
今回の使用量には余裕があるため、型別の失敗と全体容量の超過を区別できるよう、次の検証でも容量欄を記録する。
