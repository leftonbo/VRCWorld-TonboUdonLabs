# 一括保存・Rejoinによる境界検証

現在のシーンには[short・bool・byteの境界検証用70ケース](../2026-10-01-playerobject-persistence-batch-boundary/README.md)を追加し、合計121ケースにしている。
次回の操作手順はリンク先を参照。以下の51ケースは初回検証の構成と記録。

51個の独立したPlayerObjectを1シーンに配置した。
型切替、個数変更、ケース別のボタン操作は不要。
画面の「復元」は入室直後に観測した一致数で、同じ入室中に書き込んでも変わらない。
「現在」は書込み後の一致数。両者を分けて、書込んだ値を復元成功と誤認しないようにする。

## やることはこれだけ

1. `Assets/App/World/Scenes/PlayerObjectPersistenceBatch.unity` を新しいPrivateワールドとして公開し、入室する。
2. **「一括保存（全ケース）」を1回押す。** 画面の送信成功が51/51になったらRejoinする。
3. **一覧の「復元」を見る。** `N/N 保持`なら全値一致、`0/N 空/消失`なら未保存または消失、途中の数なら部分復元。再入室後に保存を押す必要はない。

初回はまだ保存していないため、復元が0一致でも正常。
TSVが必要なときだけ「結果をコピー（任意）」を押す。DesktopならCtrl+A・Ctrl+Cでコピーでき、同じボタンで閉じられる。
前の型比較シーンはそのまま使えるが、今回の一括シーンでは型ごとの再公開は不要。

## 配置したケース

| 型／構成 | 値の個数 |
|---|---|
| int | 24, 25, 26, 27, 28, 29 |
| float | 24, 25, 26, 27, 28, 29 |
| short | 50, 51, 52, 53, 54, 55 |
| long | 11, 12, 13, 14, 15, 16, 26 |
| double | 11, 12, 13, 14, 15, 16, 26 |
| bool | 26, 27, 100, 103, 104, 105, 106, 107, 108 |
| byte | 100, 103, 104, 105, 106, 107, 108 |
| stringスカラー | 27 |
| JSON文字列 | 1フィールドに4096文字 |
| int配列 | 1フィールドに27要素 |

スカラーケースは実際の `[UdonSynced]` 宣言数を個数ごとに固定した別プログラムを使う。
実行時に比較する数だけを変える方式ではない。
JSONと配列はそれぞれ1同期フィールド。
合計2395同期フィールド・2421値を比較する。
各ケースにManual Sync、VRCPlayerObject、VRCEnablePersistenceを設定し、Network IDはすべて別。

書込みは全PlayerObjectがローカル所有・復元済みになってから許可し、1フレームに1ケースずつ進める。
型比較で使ったseed=101の値を再利用する。shortは10101から、byteは1から、boolは全True。
全値を既定値と異なる値にして、ゼロ・Falseへの復元を見分ける。
入室時の自動書込み・自動初期化は行わない。

## 一括検証前の観測と仮説

ユーザー報告: floatはintと同じく27個で消失。long・doubleは26個でも消失。boolは27個で保持。
別プロジェクトでは、大きなJSON文字列をstringへ保存しても問題がなかった。
この報告は本シーンによる新しい測定とは別の先行結果として扱う。

int／floatの26個、shortの52個、long／doubleの13個は、固定幅の値部分だけならいずれも104Bになる。
型別の結果から、この付近の境界を重点的に比較する。
文字列・配列が保持される場合は、送信データ全体の一律な上限というより、固定幅スカラーを扱う保存領域やエンコード経路の違いが候補になる。内部実装の原因は未確定。

画面の「値B」は型の固定幅×個数で、フィールド識別情報・ヘッダ・圧縮等を含まない。
「送信B」はOnPostSerializationのbyteCount。復元後のセッションでは、まだ送信していないため「—」になる。
送信成功51/51は送信結果であり、クラウド保存完了の通知ではない。成否はRejoin後の復元列で判定する。
型の幅と送信byte数の区別は[公式Network Details](https://creators.vrchat.com/worlds/udon/networking/network-details/)に基づく。

## 実クライアントのRejoin結果（2026-10-01）

ユーザー提供の51ケースのTSVを[生データ](raw-client-restored-20261001-100401.tsv)としてそのまま保存した。
エクスポート日時は2026-10-01T10:04:01.4430117+09:00。保存操作の日時とは別。
クライアントの版・プラットフォームは今回のTSVに記録されていない。

| 型／構成 | 全値保持した個数 | 全値が既定値に戻った個数 |
|---|---|---|
| intスカラー | 24, 25, 26 | 27, 28, 29 |
| floatスカラー | 24, 25, 26 | 27, 28, 29 |
| shortスカラー | 未観測 | 50, 51, 52, 53, 54, 55 |
| longスカラー | 11, 12, 13, 14, 15 | 16, 26 |
| doubleスカラー | 11, 12, 13, 14, 15 | 16, 26 |
| boolスカラー | 26, 27 | 100, 103, 104, 105, 106, 107, 108 |
| byteスカラー | 未観測 | 100, 103, 104, 105, 106, 107, 108 |
| stringスカラー | 27 | なし |
| JSON文字列 | 1フィールド・4096文字 | なし |
| int配列 | 1フィールド・27要素 | なし |

全ケースで復元一致数と現在一致数は同じ。部分一致はなく、失敗ケースの現在値はすべて0またはFalseだった。
測定した範囲では、int／floatは26と27、long／doubleは15と16の間で結果が変わる。
shortの50未満、boolの28〜99、byteの100未満は未測定なので境界はまだ確定していない。

**固定幅の値部分の合計に一律の上限がある、という先行仮説では説明できない。**
long／doubleの15個（120B）は保持される一方、shortの50個（100B）は全値が既定値になる。
また、同じint27値・108Bでも27スカラーフィールドは既定値に戻り、1配列フィールドは保持される。
stringの27スカラーフィールドも保持されるため、型によらず26フィールドまでという説明も成り立たない。
型やフィールドごとのエンコード・管理情報を含めたサイズ制約は候補として残るが、内部実装や閾値は未確定。

全行のpost_success／sent_bytesはunavailableで、cloud_commit_ackもunavailable。
今回のTSVはRejoin後の観測であり、退出前の全ケース書込み成功や実送信サイズを独立に証明するものではない。
未保存と保存後の消失の区別には、このTSV以外の保存時の観測が必要。
EditorのClientSimで全ケース保持された先行結果とは分けて扱う。

## 検証記録

以下はすべて確認済み。EditorのClientSimでは全ケースが保持されたが、これは実クライアントでの境界の成否を示さない。
short・byteは値だけでなくVM上の実行時型がInt16・Byteであることも確認した。
共通ヘルパーからobjectとして返す際、単純な数値キャストではInt32になったため、Convert.ToInt16／ToByteで狭い型を維持するようにした。

- `editor-validation.txt`: コンパイル後の同期フィールド数・型、51個のマーカー、Network ID、UI接続。
- `editor-live-check.txt`／`raw-editor-written.tsv`: 実際のClientSim Udon VMから一括書込みし、実行時の型・値と表示を検証。
- `editor-restoration-check.txt`／`raw-editor-restored.tsv`: ClientSim再入室の自動表示と自動書込みなしを確認。実クライアントの保存境界とは別。
- `client-compile.txt`: クライアント向けUdonコンパイルのみ。Unityビルド、VRChat起動、アップロードは未実施。

再現チェックは `Tools > PlayerObject Persistence > Batch` のメニューから実行できる。
`Play Fresh Editor Check` はこの新シーン専用のClientSim保存ファイルをバックアップして開始する。元の実験シーンの保存データは対象にしない。
全ケースの復元を待って `Begin Live Editor Check`、書込みが終わってから `Finish Live Editor Check` を実行する。
停止後に通常のPlayで入り直し、`Check Editor Restoration` で確認できる。
